|---|---|---|---|

| D-002 | Native Kotlin app (not Capacitor). | Approved | 2026-11-09 |
| D-003 | Repo `mrmundysr-sudo/Touch_share`; work on `claude/touch-share-v1`; no merge to `main` or release without owner approval. | Approved | 2026-11-09 |
| D-004 | v0.1 uses plain HTTP with an unguessable per-session token on a trusted hotspot/LAN. (Superseded by D-016: HTTPS is no longer scheduled.) | Approved | 2026-11-09 |
| D-005 | Touch-Modules registry was not accessible from this session, so no studio component was reused. Owner to grant access or confirm none applies before 0.2. | Open | 2026-11-09 |
| D-006 | Libraries: NanoHTTPD 2.3.1 (BSD-3), ZXing core 3.5.3 (Apache-2.0). Both permissive. | Proposed | 2026-11-09 |
| D-007 | Received files saved to `Download/TouchShare` via MediaStore; no storage permission requested. | Proposed | 2026-11-09 |
| D-008 | Market research done (docs/MARKET_RESEARCH.md). Differentiator to build on: browser-only receiver, no ads/accounts. Evaluate LocalSend protocol compatibility before choosing the 1.0 transport. | Proposed | 2026-11-09 |
| D-009 | Remote ("from anywhere") sharing, if built, will be an optional **beta** using WebRTC data channels with STUN and a tiny signaling service, and **no TURN relay**, to keep running costs near zero. Local same-network sharing stays the primary feature. The app must label it honestly ("works on many networks, not all"), fail clearly after a timeout, and fall back to the local QR flow. Relay can be reconsidered later if demand and budget justify it. Needs a privacy policy and a measured success rate on real networks before release. | Approved | 2026-11-09 |
| D-010 | Visual workflow: Claude writes `visual/TouchShare_needs.json` (builder needs@1, branch `claude/needs-template` of app-visual-builder); owner fills it in the builder and returns the exported zip; Claude wires art by page and file key. Kept deliberately simple: 6 pages (Home, Sending, Receiving, Allow device, Web page, App icon), mostly one finished picture per page plus clickable/live regions; no button states or PSD layers. QR, text and progress stay live. Receiving phone's browser page is themed too. | Approved | 2026-11-09 |
| D-011 | Device approval is keyed on a random browser cookie (`ts_dev`), not the IP, so two phones behind one address are approved separately. A denied device's IP stays blocked for the session. At most 5 devices can wait at once (extra get HTTP 429). Approval is always on in 0.2 (no off switch yet). | Approved | 2026-11-10 |
| D-012 | The server runs inside a foreground service (type dataSync) so sharing continues when the app is backgrounded; session state lives in an in-process holder the screen reads. Session ends when the user taps Stop or the service is killed. | Approved | 2026-11-10 |
| D-013 | Visual wiring: art is loaded by permanent page id (page_01..page_06) from `app/src/main/assets/art/art-config.json`, generated by `tools/prepare_art.py` from the Visual Builder export (images converted to WebP, regions read from the artist's layer file and stored as fractions). Screens are letterboxed, never cropped, so tap areas always line up. PSDs and the 36 MB zip chunks are not shipped in the app. Sending and Receiving share the same art by owner's choice (same as the original app). | Approved | 2026-11-10 |
| D-014 | The browser pages (download, upload, waiting) use the web mockup (page_05) as their background and are served from the phone under `/assets/` (token required, open to devices still waiting for approval). Only .webp/.png under `art/` can be served. | Proposed | 2026-11-10 |
| D-015 | Android's system permission dialogs cannot be themed. Ask for notifications only on the first share, after a themed explainer pop-up, and remember the answer (asked once). Sharing works without the permission; only background approval alerts are lost. | Proposed | 2026-11-10 |
| D-016 | Plain HTTP is the supported mode: Touch Share is for your own hotspot or a trusted private Wi-Fi. HTTPS is not scheduled; at most an opt-in "Secure mode" later if users ask (browser certificate warning is the cost). The README and docs say: use it on your own hotspot or a Wi-Fi you trust. | Approved | 2026-11-10 |
| D-017 | Resume design: downloads use standard HTTP Range (+ ETag, If-Range, HEAD); uploads use sequential 1 MB chunks sent as form POSTs (raw PUT stalled on iOS, see CHANGELOG 0.4.3) with a start/status/chunk protocol, written straight to the final destination (pending MediaStore item), with a free-space check. Resume works within one session only (Stop discards partials). The page remembers the upload id so reopening the page and choosing the same file continues. | Approved (proven on device 2026-11-10) | 2026-11-10 |
